## 5. 저장·검색 방식 (코드 변경 없음, 조사만)

### A. 비자 정책 파이프라인 재사용 (`policy_documents` + Mongo `visa_policy_chunks` + 승인분만 검색)

| 확인 항목 | 코드에서 확인한 것 |
|---|---|
| 검색이 visa_type으로 거르는지 | `retrieval.build_pipeline`은 `visa_types`가 있을 때만 `{"visa_types": {"$in": …}}`로 거른다. 비우면 **승인된 청크 전체**를 검색한다. 그래서 금융 문서를 넣으면 visa_types를 비운 비자 검색에 금융 조문이 섞이고, 그 반대도 생긴다. 도메인을 가를 필터 필드(예: domain)가 없다 |
| visa_type_code를 비워도 되는지 | 안 된다. `ChunkRecord.visa_types`와 Mongo `$jsonSchema`가 최소 1개를 요구한다. 검색 인자의 비자 코드는 `^[A-Z]-\d…` 형식만 받는다. manifest preflight는 domain=finance를 `finance storage contract unconfirmed`로 막는다 |
| source_type LAW·ADMIN_RULE·GUIDE | 이미 있는 값이다(`law`, `admin_rule`, `guide`) |
| effective_from/to로 현행만 검색 | 청크에 필드는 있다. 하지만 값은 manifest 문서 항목 하나에서 오고(조문 단위 불가), 검색 파이프라인은 시행일로 거르지 않는다. 현행 판단은 MySQL의 `policy_document_id`별 현재 버전과 `document_version` 일치로만 한다 |
| 운영 반영에 BE 변경 | 문서마다 MySQL `policy_documents` 행(BE)이 있어야 하고, 승인 상태를 Spring gateway가 확인한다. 비자 코드가 없는 행이 BE 스키마에서 허용되는지는 이 레포에서 확인할 수 없다(확인 필요) |
| 챗봇 sources type | `POLICY_DOCUMENT`(id = policy_document_id)를 그대로 쓸 수 있다 |
| 운영 적재 절차 | manifest 항목(공식 URL·버전·검토·policy_document_id) → preflight → 적재 작업(policy_ingest) → BE 승인 → publication이 활성화 |

### B. 별도 도메인 (상품 RAG처럼)

| 확인 항목 | 내용 |
|---|---|
| 동작 방식 | 상품 RAG(`app/products/search.py`)처럼 서버 시작 때 문서 폴더를 읽어 메모리 안에 조문 단위 색인을 만든다(Mongo·BE 없음). 시행 예정 판은 색인에서 뺀다 |
| 오늘 운영에서 검색까지 | 된다. 폴더 경로 설정과 `LOAD_MODEL_ON_STARTUP=true`만 필요하다 |
| 문서 기준 유지 | manifest 항목(공식 URL·버전·검토·시행일)을 같은 preflight로 검사한 파일만 색인에 넣게 하면 된다(BE 없이 코드 안에서). 승인 상태 저장은 없다 |

### 추천: B → **결정: B (2026-11-17)**

- 별도 도메인(메모리 색인)으로 간다. sources는 처음에는 비우고, 답변 본문에 조문·시행일을 인용한다(새 계약 0).

- ① 오늘 운영에서 검색까지 동작: **B만 된다.** A는 BE 행, finance 도메인 해제, visa_types 필수 처리, 도메인 필터가 필요하다.
- ② 문서 기준(manifest preflight) 유지: B도 같은 preflight를 적재 조건으로 쓰면 유지된다.
- ③ 새 계약 최소: B는 sources type 하나가 남는다. 처음에는 답변 본문에 조문·시행일을 인용하고 sources는 비워 두면 새 계약이 0이다. sources 저장은 type을 정한 뒤 붙인다(결정 필요).
- A를 고르면 비자 검색에 금융 조문이 섞이는 문제(도메인 필터 없음)를 먼저 풀어야 한다.

### 지표로 세 안을 가를 수 있는지 (판단)

- **Recall@5만으로는 가르기 어렵다.** 규정·법령 청크가 16~25개로 적고 정답의 절반 가까이가 제4-4조 한 단위다. 한국어 검색어는 천장에 붙을 가능성이 크다. 32회에서 한 문항 차이는 0.031이라 작은 차이는 구분되지 않는다.
- 그래서 보조 지표로 **핵심 사실 포함@5**(그 문항의 핵심 사실 인용이 모두 상위 5 청크 안에 있는 비율)를 같이 보자고 제안한다. 다문서·다조문 문항(A01·A03·A05·A06·A08·A13)에서 차이가 날 수 있다.
- 영어 검색어는 영어 가이드북 청크로 쏠릴 가능성이 크다. #47처럼 **검색어 언어가 방식보다 큰 변수**일 수 있으니 언어별로 따로 보고한다.
- **지표와 선택 규칙(2026-11-17 결정)**: Recall@5(주) + 핵심 사실 포함@5(보조) + MRR@5, 한국어·영어 검색어를 따로 낸다.
  고르는 순서: Recall@5 → 핵심 사실 포함@5 → MRR@5 → 단순함(① > ② > ③). 각 단계에서 1문항 이하 차이는 동점으로 남긴다.
