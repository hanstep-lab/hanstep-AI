# OCR Worker 속도 측정 (#110, 2026-11-19~20)

## 결론

- 기본값
  - `OCR_DET_MODEL=PP-OCRv5_mobile_det`
  - `OCR_MAX_SIDE=1280`
  - `OCR_CPU_THREADS`는 비움(PaddleOCR 기본값 10). 값은 compose에서 정한다(hanstep-backend 이슈, 아래)
- 앱과 같은 1500px 사진에서 필수 5개(등록번호·성명·국가·체류자격·발급일)와 나머지 3개를 모두 읽으면서 가장 빠른 조합이다(7절).
- 운영이 30초 안팎이던 주된 원인 세 가지
  1. **ocr-worker CPU 상한 `cpus: "2"` + PaddleOCR 기본 스레드 10.** 로컬 CPU 2개·기본 스레드 기준선이 22.8~27.5초로, 운영 실측 29.6~31.8초와 비슷하다. 같은 server_det도 스레드를 2로 맞추면 7.4~13.2초다
  2. **무거운 검출 모델(server_det).** mobile_det는 같은 조건에서 필드 정확도가 같고, 스레드를 맞추면 1.3~1.4초다
  3. **다른 작업과 겹침.** CPU 2개·기본 스레드에서 다른 컨테이너가 CPU 4개를 쓰면 mobile_det도 11~14.5초로 늘어난다. 스레드 2면 1.8~2.2초다(6절)
- 사진 크기는 앱 경유 사진(1500px)에서는 주된 원인이 아니다. 1280으로 줄이면 1500 그대로보다 약 30% 더 빠르다.

| 조건(1500px 사진 3장 중앙값) | develop(server_det, 스레드 10) | 이 PR 기본값 + 스레드 = CPU 상한 |
|---|---|---|
| CPU 2개(지금 운영 compose 상한) | 22.8 / 26.0 / 27.5초 | **0.88 / 0.91 / 0.94초**(mobile_det, 1280, 스레드 2) |
| CPU 8개(내일 c7i.2xlarge 8 vCPU) | 7.4 / 8.5 / 9.3초 | **1.08 / 1.07 / 1.02초**(mobile_det, 1280, 스레드 2) · 1500 그대로면 스레드 4가 1.27 / 1.43 / 1.36초 |
| CPU 8개 + 다른 작업이 CPU 4개 사용 | 8.4 / 10.2 / 10.1초 | 1.54 / 1.65 / 1.73초(mobile_det, 1500, 스레드 4) |

- **스레드를 비워 두면(이 PR만 배포하면) 시간이 이렇게 나온다**
  - CPU 2개: 6.2~6.5초(mobile_det, 1500)
  - CPU 8개: 3.5~4.5초
  - CPU 2개에 다른 작업이 겹치면: 11~14.5초
- 그래서 목표(c7i에서 3초 이내, 배포 직후 부하에도 유지)는 compose에서 `OCR_CPU_THREADS`를 컨테이너 CPU 상한(또는 물리 코어 수) 이하로 정해야 맞는다.

## 1. 조사 (코드 수정 전)

| 항목 | 내용 |
|---|---|
| 흐름 | `worker/processor.py` `_recognize`(R2 → 임시 파일, `fetch_ms`) → `deps.recognize`(`ocr_ms`) → `worker/runner.py` 엔진 스레드 → `pipeline/engine.py` `recognize` → `PaddleOCR.predict(파일 경로)` → `extract_fields` |
| 전처리 | 없었다. PaddleOCR(paddlex)이 `cv2.imdecode(IMREAD_COLOR)`로 파일을 읽는다 |
| 크기 설정 | `text_det_limit_type=min`, `limit_side_len=64`, `max_side_limit=4000`. 짧은 변이 64보다 작을 때만 키우고 긴 변은 4000까지 둔다. 원본 4032×3024는 4000×3000으로만 줄어 검출에 들어갔다 |
| 스레드·mkldnn | PaddleOCR 기본 `cpu_threads=10`, `enable_mkldnn=True` |
| 라벨 | `MODEL_VERSION = "ppocrv5-ko-v0lite"` 고정. 실제 모델은 server_det + korean mobile rec |
| Spring | `documents.ocr_model_version`(VARCHAR 60)에 저장하고, 같은 결과 재전송 판단(`sameAsRecorded`)에만 비교한다. 라벨이 바뀌어도 저장·조회는 그대로다. 배포 직전 처리분을 새 Worker가 다시 보내면 라벨이 달라 409가 날 수 있다(드묾) |
| EXIF 회전 | `cv2.imdecode(IMREAD_COLOR)`가 적용한다(EXIF 6, 300×100 → 100×300 확인) |
| 모델 캐시 | `/root/.paddlex/official_models`. Dockerfile이 빌드 때 `load()`로 기본 조합만 넣었다(server_det·rec). mobile_det는 없어서 그대로면 첫 실행 때 다운로드 |

## 5. 리사이즈 (mobile_det, mkldnn 켬)

| 조합 | 처리 크기 | CPU 2개(스레드 2) | CPU 8개(스레드 2) | 필수·8개 |
|---|---|---|---|---|
| 1500 그대로(`OCR_MAX_SIDE` 1500 이상 또는 0) | 1500×950 / 1500×1125 | 1.30 / 1.32 / 1.44 | 1.88 / 1.64 / 1.49 | 5/5·8/8 |
| `OCR_MAX_SIDE=1280` | 1280×811 / 1280×960 | **0.88 / 0.91 / 0.94** | **1.08 / 1.07 / 1.02** | 5/5·8/8 |

- 앱이 1500px로 줄여 올리므로, `OCR_MAX_SIDE`는 1500 이상이면 아무 효과가 없다. 그래서 후보는 1280·1500만 봤다.
- 1500 → 1280 축소 시간은 수 ms다. 원본 4032×3024 → 1280×960은 51ms다(기본값 엔진 1회, CPU 2개·스레드 2, 1.46초에 등록번호·성명·체류자격을 읽음).
- `OCR_MAX_SIDE`는 앱을 거치지 않은 큰 사진의 메모리도 막는다(원본 그대로면 7.75GB).
- 검출 크기 설정(limit_type=min 64, max 4000)은 1280·1500 입력을 다시 줄이거나 키우지 않는다(32의 배수로만 맞춤).

  - 스레드는 CPU 상한·물리 코어 수 이하로 둔다.

## 9. 로컬과 운영의 차이

- **CPU 상한이 같으면 거의 같다.** 로컬 CPU 2개·develop 기준선 22.8~27.5초, 운영 29.6~31.8초.
- 남은 차이(운영이 10~25% 느림)의 원인 후보는 아래와 같다. 모두 로컬에서는 재지 않았다(미측정).
  - CPU: 운영 AMD EPYC 7571(2017, AVX-512 없음, mkldnn 최적화가 덜 맞을 수 있음) vs 로컬 i5-1135G7(AVX-512)
  - 같은 서버의 Spring·ai-server·Mongo·RabbitMQ와 동시 실행
  - 운영 사진은 실제 촬영이라 글자 상자 수가 다를 수 있음
- 지연님 리눅스 PC(최신 CPU, 상한 없음)에서 1초대라는 관찰은 이 표의 "스레드 = 물리 코어" 결과(1.3~1.4초)와 맞는다.
